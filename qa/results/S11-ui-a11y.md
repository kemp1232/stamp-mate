## Defects

### Defect S11-D1 — Staff action buttons (Add Stamp / Undo / Redeem) are 36px tall, below the 44px minimum tap target
- **Severity:** Medium
- **Test case ID(s):** S11-002
- **File:line:** `src/components/ui/button.tsx:27` — `size: { lg: "h-9 gap-1.5 px-2.5 ..." }` (Tailwind `h-9` = 2.25rem = **36px**, not 44px). Consumed by `size="lg"` in `src/components/stamp-controls.tsx:56,76` (Add Stamp, Undo Last Stamp) and `src/components/redeem-reward-button.tsx:31` (Redeem Reward).
- **Repro:** Load `/staff/cards/[cardToken]` on a 390×844 mobile viewport (or any device), measure `getBoundingClientRect()` of any of the three buttons — height is 36px. Also measured: the scanner's manual-entry "Go" button (40×32) and the "Scan" link on `/staff` (57×32) are similarly undersized.
- **Observed vs Expected:** Observed: 336×36 px for the three primary staff action buttons (full width, so only the height dimension fails). Expected (per WCAG 2.5.5/2.5.8 and this test plan's own S11-002 criterion): ≥44×44 CSS px, since these are the primary buttons staff tap repeatedly, often one-handed, mid-transaction, on a phone.
- **Suggested fix:** Either raise the "lg" button size token to `h-11` (44px) globally, or add an explicit `min-h-11` / `h-11` override on these three specific staff-facing buttons.

### Defect S11-D2 — SD-13 confirmed: no `error.tsx`/`not-found.tsx`/`global-error.tsx` anywhere in the app
- **Severity:** High
- **Test case ID(s):** S11-007
- **File:line:** absent from `src/app/**` entirely (no such files exist at any level — checked via full recursive filesystem walk).
- **Repro:** `find src/app -iname 'error.tsx' -o -iname 'not-found.tsx' -o -iname 'global-error.tsx'` → no results. Navigate to any nonexistent route, e.g. `/this-route-does-not-exist-xyz` → served Next's raw built-in default error page (unstyled, `.next-error-h1` boilerplate), not a branded StampMate page.
- **Observed vs Expected:** Observed: any uncaught exception thrown inside a Server Component (e.g. an unexpected DB error during `addStamp`'s non-`StampActionError` path, or simply visiting an unmapped URL) falls through to Next.js's default, unbranded error/404 experience. All of the app's *controlled* errors (validation, "not found" lookups) are handled gracefully via `ErrorState`/`EmptyState` components — but genuinely unexpected throws are not caught anywhere. Expected: a branded `error.tsx` (with a "Try again" affordance) and `not-found.tsx` at minimum at the `src/app` root, ideally also under `dashboard/` and `staff/`.
- **Suggested fix:** Add `src/app/error.tsx`, `src/app/not-found.tsx`, and `src/app/global-error.tsx` per Next.js App Router conventions, styled consistently with the rest of the app's `ErrorState` component.

### Defect S11-D3 — Dark mode is entirely non-functional (dead `.dark` CSS block, no class-toggling mechanism)
- **Severity:** Medium
- **Test case ID(s):** S11-016 (also affects the "dark" half of S11-015's measurements, which turned out to be a duplicate of the light measurements)
- **File:line:** `src/app/globals.css:5` (`@custom-variant dark (&:is(.dark *));` — class-gated, not media-query-gated) and the `.dark { ... }` variable-override block at `globals.css:86-110+`. No file anywhere in `src/**` (`.tsx`/`.ts`) ever adds, toggles, or otherwise sets a `dark` class on any element (confirmed via `grep -rn "classList.add|classList.toggle|documentElement.class|next-themes|ThemeProvider" src` → zero matches), and there is no `ThemeProvider`/`next-themes` dependency wired into `src/app/layout.tsx`.
- **Repro:** With a browser/OS set to prefer dark mode (or via Playwright's `page.emulateMedia({colorScheme:'dark'})`), load any page (e.g. `/card/[token]`) and inspect `document.documentElement.className` (never contains `dark`) and `getComputedStyle(document.body).backgroundColor` (identical to the light-preference render).
- **Observed vs Expected:** Observed: the app always renders with light-mode CSS variables, regardless of the user's OS/browser color-scheme preference; every `dark:` Tailwind variant in the codebase (e.g. the emerald "redeemed" banner `dark:bg-emerald-950 dark:text-emerald-300` in `src/app/staff/cards/[cardToken]/page.tsx:63`, and the emerald success text `dark:text-emerald-400` in `stamp-controls.tsx`/`program-form.tsx`) is unreachable dead code. Expected (per the test plan's S11-016 criterion "Toggle OS dark theme ... dark: variants render legibly"): the app should switch to the dark palette already defined in `globals.css` when the OS/browser prefers dark.
- **Suggested fix:** Either (a) switch the Tailwind dark-mode strategy to media-query-based (`@custom-variant dark (&:is(@media (prefers-color-scheme: dark)))` or Tailwind v4's `dark:` media default) if no manual toggle is planned, or (b) wire up a `ThemeProvider`/`next-themes` (or a small inline script in `layout.tsx`) that sets the `.dark` class from `prefers-color-scheme` (and optionally a user toggle) on the `<html>` element.

### Defect S11-D4 — `/login`, `/register`, `/card/[token]`, and `/staff/cards/[token]` have zero heading elements
- **Severity:** Low
- **Test case ID(s):** supplementary finding (heading-hierarchy audit performed per the briefing's "Labels/alt text" focus area; not a separately numbered TEST-PLAN.md case)
- **File:line:** `src/app/login/page.tsx` and `src/app/register/page.tsx` use `<CardTitle>` for "Log in" / "Create your business account" (`src/components/ui/card.tsx:32-41` — `CardTitle` renders a plain `<div>`, not an `<h1>`–`<h6>`); `src/app/card/[cardToken]/page.tsx` and `src/app/staff/cards/[cardToken]/page.tsx` render `CustomerSummaryCard`, which also only uses `CardTitle` (a `div`) for the customer's name (`src/components/customer-summary-card.tsx:49`) — neither page has any heading element anywhere.
- **Repro:** `page.evaluate(() => document.querySelectorAll('h1,h2,h3,h4,h5,h6').length)` on any of the 4 routes → `0`. Confirmed by contrast: `/dashboard`, `/dashboard/program`, `/dashboard/customers`, `/dashboard/stats`, `/join/[slug]`, `/staff`, `/staff/scan` all correctly render exactly one `<h1>`.
- **Observed vs Expected:** Observed: screen-reader users navigating by heading (a primary a11y navigation pattern) find no landmark on the login/register/card pages — there is nothing to jump to. Expected: every page should have exactly one `<h1>` identifying its primary content, consistent with the other 7 routes in the app that already do this correctly.
- **Suggested fix:** Either change `CardTitle` to render a heading tag by default (with an `as`/`level` prop for pages where a `div` is intentional), or explicitly wrap the "Log in" / "Create your business account" / customer-name text in an `<h1>` on these 4 pages.
