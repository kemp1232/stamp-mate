# S9-redemption — Results

Covers `redeemReward` in `src/lib/actions/rewards.ts`. Executed live against `http://localhost:3100` and the local Supabase Postgres DB (`postgresql://postgres:postgres@127.0.0.1:56322/postgres`), using isolated tenants created per case via `seedTenant()`/`createBusiness()` etc. (unique `uid()`-suffixed rows only). Script: `S9-redemption/s9.js` (run with `node S9-redemption/s9.js` from `<SCRATCH>/qa`). Full run log with raw evidence: see the `RESULTS_JSON` block printed by that script.

**Method note:** server-action POSTs were replayed with plain `fetch()` + `FormData`, using a `next-action` id captured once from a real Playwright-driven click (see `S9-redemption/probe.js`). Confirmed the id is stable across calls/cardTokens within this dev-server session, and that `cardToken` travels as a plain multipart field (not baked into the action reference), so it was safe to swap per case. Response shape observed: successful redeem → HTTP 303 with `x-action-redirect: /staff/cards/<newToken>?redeemed=1;push`; rejected-with-message → HTTP 200 with an RSC body containing `{"error":"..."}`; server `redirect()` to `/dashboard` (authz) → HTTP 303 with `x-action-redirect: /dashboard;push`.
