# S2-authz-isolation — Results

Suite script: `qa/S2-authz-isolation/run.js` (run via `npx tsx`). Covers `src/proxy.ts`, `src/lib/authorization.ts`, the dashboard/staff layouts, and cross-business scoping, against the live app at `http://localhost:3100` and the local Supabase Postgres DB.

**Setup:** Two fully-seeded tenants were created for this run via the harness (`seedTenant()`): **Tenant A** (Owner A, Store A, Program A required=5, Customer A, Card A) and **Tenant B** (Owner B, Store B, Program B required=5, Customer B, Card B) — analogous to the plan's "Business A / Business B" fixtures, plus a **Staff A2** user (STAFF-role membership in Business A only, no OWNER membership anywhere). All assertions are scoped to these specific seeded ids, never to global table counts (per the QA hard rules — this DB is shared with other concurrent QA runs).

## Defects

### Defect 1 — Expired DB session still authenticates while the signed cookie cache is fresh (new finding, not in original suspected-defect list)
- **Severity:** High
- **Test case ID(s):** S2-005
- **File:line:** `src/lib/auth.ts:12-15` (`session.cookieCache = { enabled: true, maxAge: 300 }`); the trust boundary is inside Better Auth's own session-resolution path (`auth.api.getSession()` used by `getCurrentUser()`/`requireUser()` in `src/lib/authorization.ts:8-11`), which is configured to serve straight from the signed `better-auth.session_data` cookie without a DB round-trip for up to 5 minutes.
- **Repro:**
  1. `signUpUser()` (real HTTP sign-up) → obtain the full cookie header (`better-auth.session_token` + `better-auth.session_data`).
  2. `UPDATE session SET "expiresAt" = now() - interval '1 day' WHERE id = <that session's id>` directly against the DB.
  3. `GET /dashboard` with the **full** original cookie header → **200**, page renders `"Signed in as <user email>"` — the user is still fully authenticated.
  4. Repeat step 3 with only the `better-auth.session_token` cookie (cache cookie stripped) → correctly `307 Location: /login`.
- **Observed vs Expected:** Observed: an out-of-band session invalidation (DB-level `expiresAt` mutation, e.g. from an admin "force logout"/"revoke session" action or an automated expiry job) has **no effect** for up to 5 minutes if the client already holds a cached, signed session cookie from before the mutation — the app keeps trusting the stale cache. Expected (per plan): "server session invalid → redirect /login" unconditionally.
- **Suggested fix:** This is an inherent trade-off of Better Auth's `cookieCache` feature (perf vs. freshness) rather than a bug unique to this app, but it should be a **deliberate, documented decision** given this app's security model (staff/owner session revocation, e.g. after offboarding an employee, currently has an up-to-5-minute grace window). Either shorten `maxAge`, disable `cookieCache` for the staff/owner surfaces where prompt revocation matters, or explicitly accept and document the window.

### Defect 2 — Owner-only page authorization redirects from nested Server Components are not literal HTTP 307s (low-severity, hardening item)
- **Severity:** Low
- **Test case ID(s):** S2-006, S2-007 (both still PASS on the actual security property; this is a status-code/observability nuance, not a data leak)
- **File:line:** `src/lib/authorization.ts:60-73` (`requireOwnedBusiness()`), called from `src/app/dashboard/program/page.tsx`, `src/app/dashboard/stats/page.tsx`, `src/app/dashboard/customers/page.tsx` — all *nested inside* `src/app/dashboard/layout.tsx`, whose own `requireUser()` check has already succeeded and started streaming a `200` response by the time these page-level checks run.
- **Repro:** As STAFF A2 (valid session, no OWNER membership), `curl -i http://localhost:3100/dashboard/program -H "Cookie: <staff session>"` → raw response is `HTTP/1.1 200 OK` containing an embedded RSC flight marker `NEXT_REDIRECT;replace;/dashboard;307;` rather than an HTTP-level `307`.
- **Observed vs Expected:** Observed: any HTTP client that doesn't execute JavaScript (curl, monitoring probes, some scrapers/bots, accessibility/security scanners expecting a `3xx`/`4xx`) receives a `200` with an empty/loading page shell instead of a clear redirect or error status — it is not redirected and does not see any protected data either. Real browsers (which run the returned client JS) do correctly navigate to `/dashboard`, as confirmed with Playwright. Expected: a consistent `307` at the HTTP layer for every unauthorized access, matching the middleware-level and layout-level (`requireUser()`) behavior seen in S2-001/S2-002/S2-004.
- **Suggested fix:** No data is exposed (the throw happens before any protected query result is rendered), so this is not an exploitable authorization bypass. If HTTP-level consistency matters (e.g. for external monitoring/security tooling), move the owner-check as early as possible (e.g. into the `/dashboard/program`, `/dashboard/stats`, `/dashboard/customers` routes' own thin wrapper executed before any layout content streams, or accept this as an inherent Next.js App Router streaming trade-off and document it).

### Defect 3 (informational, not a defect) — `S2-016` initial false positive
- Not a product defect — a QA-script fix. `seedTenant()`'s default customer name (`"QA Customer"`) is identical across all tenants seeded via the harness, which produced a false-positive isolation failure in the first run of S2-016 (matching Owner A's *own* customer, not a leak of Business B's data). Fixed by giving each tenant's seeded customer a unique name before asserting; re-run confirmed true cross-business isolation holds. Documented for anyone reusing this harness pattern.
